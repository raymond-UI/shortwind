Shortwind Cloud

How the payment system works

Stripe billing, ported from Realm · account-scoped · test mode on the dev deployment

1 — The model in one line

Publishing and serving pages are free. A custom domain requires a paid plan.

Serving a page costs almost nothing (a viral page is basically free). What costs money — and what attracts phishing abuse — is a custom domain: a real certificate on a name someone else controls. So that is the one thing we gate behind payment.

An account with no subscription is treated as free by default — nothing to configure.

2 — What happens when someone upgrades

1
Click “Upgrade to Pro” in the dashboard’s Billing tab.
The button calls createCheckoutSession.
2
Redirect to Stripe’s hosted checkout.
We never see or store card details — Stripe handles the whole payment page.
3
Customer pays.
Stripe creates the subscription against the account.
4
Stripe calls our webhook.
A signed event hits /stripe/webhook; the Convex component records the subscription. Verified live: returns HTTP 200.
5
The account is now Pro.
The summary query reflects it, and the custom-domain gate starts allowing binds.

Managing or cancelling later goes through Stripe’s own customer portal (the “Manage subscription” button) — same pattern, no card handling on our side.

3 — The moving parts

Frontend

BillingView in the dashboard shows the plan and the Upgrade / Manage buttons. It reads through the data seam, so it never touches Stripe directly and stays fully testable.

Backend

billingStripe wraps the Stripe component: summary (read the plan), createCheckoutSession, portalUrl, and the signed webhook.

Enforcement

The custom-domain bind path checks the plan first. Free → rejected with NOT_ENTITLED before any Cloudflare call. The rules live in one pure file (billing_limits).

Plan lookup

A small seam resolves “what plan is this account?”. Closed by default (treats everyone as free) until the real Stripe-backed resolver is switched on at startup.

Why account-scoped, not team-scoped

Realm (the template this came from) bills a whole organization with member roles. Shortwind Cloud bills a single account (one login = one subject), so there are no roles — the signed-in owner always manages their own plan.

5 — Next steps (simple version)

1. Flip the plan lookup “on.”
One line at startup switches the plan resolver from “everyone is free” to the real Stripe-backed one. Until then the custom-domain feature is effectively off (every account reads as free, so binds are blocked). Small change; highest priority.
2. Do one real test checkout.
Log into the dashboard, click Upgrade, pay with a Stripe test card, and confirm the account flips to Pro and a custom-domain bind then succeeds. The webhook half is already proven; this proves the checkout half.
3. Set up production separately.
When this ships to prod, prod needs its own Stripe live keys, its own price, and its own webhook endpoint — the same steps, pointed at the production account. Test-mode data does not carry over.
