1. Summary
AI coding agents — Claude Code, Codex, Gemini CLI, and others — generate large volumes of self-contained HTML as a routine byproduct of their work: dashboards, product requirement docs, analytics views, status pages, issue write-ups, trip plans. Today that output dies in a session folder or a chat transcript. There is no purpose-built way for an agent to take a page it just produced and put it on the public web at a durable address.
This product is that missing distribution layer. The primary user is the agent, not the human. The agent, acting on the user's account, publishes an HTML file and receives back a shareable URL. It can update that page in place, list what already exists so it does not create duplicates, control visibility, and bind a custom domain. The human's role shifts from author to operator: they grant the agent access, set policy, and oversee — they do not paste HTML into a dashboard.
The core thesis: agent-generated HTML is becoming a standard output format, and standard output formats need standard distribution. Markdown got Gists; images got image hosts; agent-built HTML has nothing built for it yet. We build that distribution layer, agent-first and cross-agent, before the category settles.
Why now: Anthropic shipped live, in-session, auto-updating HTML artifacts inside Claude Code — but locked them to the org, with no public sharing. That is not an oversight; it is a liability they chose to avoid. It is also direct evidence the file-class is real and the public edge is unserved. We take the public edge and the operational responsibility that comes with it.
2. Goals and non-goals
2.1 Goals
	•	Give any agent a small, discoverable set of verbs to publish, update, find, and manage HTML pages on a user's account, with zero local state held by the agent.
	•	Make each published page a persistent, owned, addressable object — not a throwaway preview.
	•	Support custom domains on individual pages (status.acme.com is one agent-maintained file).
	•	Use Shortwind as the styling engine so authoring-by-agent costs ~40% fewer tokens, and keep published pages re-editable in compact shorthand form.
	•	Ship a credible content-moderation and legal-takedown capability from day one.
2.2 Non-goals (for v1)
	•	We do not generate the HTML. The agent authors; we host, expand, and serve.
	•	We are not a website builder, a CMS, or a multi-page site framework. The unit is a single file.
	•	No live data-binding or server-rendered pages in v1. Published pages are frozen static artifacts.
	•	No team/org collaboration surface in v1. Single operator account per workspace.
	•	No bundle/multi-file deploys in v1 (this is a fast-follow, not the launch unit).
3. Users and the core model
Primary user — the agent. Runs in a terminal or desktop app on behalf of a human. It authors HTML and calls the platform's verbs. It is stateless against the platform: it never remembers page IDs locally. To act correctly it reads the account (find/list), then publishes or updates against what it finds.
Secondary user — the human operator. Owns the account, grants the agent a scoped token, sets policy (e.g. agents may publish unlisted but custom-domain promotion needs human approval), and oversees via a dashboard and audit log. Authoring is not their job.
3.1 The account is the memory
Because the agent holds no local state, the platform is the system of record. The same user may act through Claude Code today and Codex tomorrow; local state would not survive that, but the account does. This single decision shapes the whole API: the most important verb is not publish, it is find — it is what lets a stateless agent answer “do I already have a status page?” before it spawns a duplicate.
3.2 Page identity
Identity is server-side and addressable two ways, both resolving to the same record:
	•	Canonical ID / slug — the durable primary key. The agent discovers it by querying the account, not by remembering it.
	•	Domain / path — the human-meaningful address. Publishing to status.acme.com resolves to that record.
Publishing is idempotent on a stable handle: if a page already exists at a slug or domain, the platform returns a 409 with the existing ID (“did you mean update?”) rather than silently forking. This is what makes the platform feel owned rather than a pile of orphan URLs.
4. Functional requirements — the agent API
The API is the product. The human dashboard is oversight; the agent surface is where the work happens. All verbs are REST, mirrored by a CLI and advertised through a discovery surface (Section 7).
Verb
Endpoint
Purpose
find
GET /v1/pages?q=&domain=&tag=
Load-bearing verb. Lets the stateless agent locate an existing page before acting. Rich query is what prevents duplicates.
publish
POST /v1/pages
Create a page from HTML (+ lockfile, + touched recipes). Returns id, url, version. Idempotency-keyed.
update
PATCH /v1/pages/{id}
Republish to the same URL; previous versions retained. Makes “persistent” real.
get
GET /v1/pages/{id}
Metadata + version list so the agent can confirm before acting.
delete
DELETE /v1/pages/{id}
Remove a page (see Section 8 — delete means tombstone, with quarantine for abuse cases).
visibility
PATCH /v1/pages/{id}/visibility
public / unlisted / private.
bind-domain
POST /v1/pages/{id}/domain
Privileged. Bind a custom hostname. Requires the domains:bind scope (human-gated).
The agent's loop, in motion:
	•	Human says “update the status page.”
	•	Agent calls find?q=status → gets pg_abc at status.acme.com.
	•	Agent calls update(pg_abc, html) → same URL, version bumped.
	•	If find returns empty → agent calls publish to create a new one.
Nothing is stored locally. The account is memory; identity is server-side; the agent contributes only the publish command and the HTML.
5. Styling engine — Shortwind integration
The agent authors pages using Shortwind shorthand recipes (e.g. class=“@card”) instead of long Tailwind class strings. This is where the token saving lands — at generation time, which is the expensive part — and it compounds when an agent publishes many pages.
5.1 Expansion happens once, server-side, at publish
Three options were considered. Expanding locally before publish defeats the purpose (re-introduces a build step and ships un-editable output). Expanding on every request adds latency for no benefit, since recipes do not change between requests. The chosen path: the platform expands once at publish time using the Shortwind core engine, stores the frozen Tailwind HTML + scoped CSS as the served artifact, and keeps the shorthand source alongside it. The browser gets byte-identical Tailwind off the CDN; the agent never runs a build; the source stays compact and re-editable.
5.2 A global Shortwind home, not a per-repo setup
A naive integration would require Shortwind to be set up inside the user's working repo, so the publish command could find the recipes and lockfile there. That is the wrong assumption: the agent works in arbitrary directories — scratch folders, project roots, anywhere — and must not need per-project setup. Instead, Shortwind is installed once, globally, via a one-time CLI init that creates a Shortwind home at ~/.shortwind/ containing the recipe palette, the lockfile (.shortwind-lock.json), and credentials.
The global home behaves exactly as a repo-level setup would: same recipe files, same fingerprint headers (version + content hash per recipe), same lockfile, same publish semantics. Nothing about the mechanism changes — only its location. Any agent in any directory resolves recipes from the global home with zero per-project setup. Resolution order is the standard git/npm pattern: a local repo recipes/ folder is used if present (a power-user override and a natural containment scope, see 5.5), otherwise the global ~/.shortwind/ home is the default.
The global home is singular per machine and bound to whichever cloud account is currently logged in; shortwind login switches the active account (like gh auth switch). It is authenticated to the user's cloud account via the device flow in Section 7 and stays in sync with that account's cloud palette.
5.3 Self-contained publishes (no watcher, no sync command)
The agent must never run a background watcher or remember to sync recipes. Publishing must be the only action. The fingerprint headers and lockfile make this clean: each recipe carries a content hash, and the lockfile records family versions.
So the publish is self-contained and carries its own dependencies. The publish command reads the lockfile and fingerprints from the active Shortwind home — it does not scan the HTML to discover this. It sends the page plus the lockfile plus the bodies of any locally-touched recipes (those whose content hash diverges from their fingerprint). The platform diffs the incoming lockfile against the last one it stored to know exactly what changed, applies touched bodies, versions them, and expands. The publish is the sync — recipe changes ride up to the cloud on the next publish, no separate command.
5.4 The agent is the primary recipe editor
Recipes are a folder of text files on a machine the agent already operates in. An agent that can write page.html can write ~/.shortwind/recipes/card.css — so the agent, not the human, is the most likely and most frequent recipe editor. This is on-thesis: the agent does the work, and recipes are part of the work. An agent noticing a repeated card pattern can author a @card recipe, use it across the pages it publishes, and have that recipe version up to the cloud on the next publish. The agent does not merely consume the palette; it grows it.
Decision: recipe edits flow up as freely as page publishes. No consent gate. The blast radius of a recipe edit is larger than a page edit — a shared recipe affects every future page that uses it, across every machine that syncs the palette — but three things make free-flow the right call rather than a risk. (1) Forward-only versioning makes every change recoverable: a recipe goes 0.4.0 → 0.5.0 and can be rolled back; nothing is lost. (2) Old published pages are frozen and never rebuild (5.6), so a recipe edit can never silently mutate already-shared pages. (3) The local repo recipes/ override (5.5) gives agents a scoped scratch space when they want isolation.
Required visibility: because a recipe change is higher-consequence than a page change, the audit log (Section 8 / dashboard) records recipe edits distinctly — e.g. “agent modified recipe @card (0.4.0 → 0.5.0), affects N pages on next publish.” This is visibility for the human operator, not a gate. It keeps the agent unblocked while letting the human notice and roll back if they care.
5.5 Containment via the local override
When an agent wants to change a recipe for one project without machine-wide, account-wide consequences, it edits a local repo recipes/ folder instead of the global home. Local-if-present-else-global resolution means those edits are scoped to that directory and never touch the shared palette. So casual, project-specific tweaks can be confined locally, while deliberate palette growth goes to the global home and up to cloud. This is a single, simple precedence rule — not a three-way merge — and it doubles as the blast-radius control for agent recipe editing.
5.6 Versioned forward-only; pages stay frozen
A published page is frozen Tailwind with no runtime expander and no live link back to recipes — matching Shortwind's production build output. A recipe change affects only the next publish that carries it. We explicitly do not mass-rebuild old pages when a recipe changes: a user with thousands of pages would face an absurd, unwanted fan-out. Old pages are correct historical artifacts, pinned to the recipe state of their build moment. To restyle a specific old page, the agent republishes that one page — a deliberate, single act.
5.7 Cloud palette and discovery
The cloud holds the authoritative, versioned palette per account; the global home is its synced working copy. Because expansion happens server-side at publish, a stale local copy is never dangerous — the cloud expands against its own current palette, so local staleness is cosmetic (it affects only the agent's authoring awareness, not output correctness). The agent's discovery surface (Section 7) advertises the account's current vocabulary so the agent knows which recipes exist before it writes them, and can choose to extend rather than duplicate them.
6. Technical architecture
Two facts drive the design. First, published pages are frozen static HTML + CSS, so serving is cheap, stateless file delivery. Second, all expensive, stateful work happens once, at publish. The principle: a thick publish path and a razor-thin serve path. No per-request compute on the hot path.
6.1 Serving layer (hot path — keep it dumb)
	•	R2 stores the frozen artifacts. Zero egress fees, which matters because serving HTML to the public web would otherwise be the dominant cost.
	•	A Cloudflare Worker is a pure router: resolve hostname/path to a page record (from KV cache, with Convex as cold source), stream the artifact from R2, cache at edge. No expansion, no DB write on the hot path.
	•	Cloudflare for SaaS provides custom hostnames with edge-terminated SSL, issued and renewed per hostname — the productized path for bind-domain.
6.2 Publish layer (thick path — where the work is)
On publish: authenticate the scoped token → diff the incoming lockfile against stored → resolve the recipe set → run Shortwind expand() to produce frozen Tailwind → write the artifact to R2 → version the page record in Convex → update stored lockfile state → invalidate the edge cache for that URL → return { url, version }. Expansion is fast and deterministic, so v1 can run it synchronously and return the URL in the same call.
6.3 Control plane
	•	Convex is the system of record: accounts, pages (id, slug, owner, visibility, custom domain, current version, history), recipe versions per account, recipe-edit audit events, scoped tokens, audit log. Its reactivity powers the dashboard but is deliberately kept out of the public serve path.
	•	Better Auth issues device-flow tokens and scopes. Public-page serving needs no auth; private pages add a validation step on the Worker.
6.4 Cost shape
Costs track publishes and storage, not page views. A viral page costs almost nothing to serve, and metered billing (publishes, custom domains, storage) aligns with what actually costs money. Any origin-compute-per-view design would invert this and bleed on popular pages — which is the reason for the all-static serving stack.
7. Authentication and discovery
7.1 Human login — OAuth 2.0 Device Authorization Grant (RFC 8628)
The agent runs in a terminal with no browser, so the device flow is the correct, settled pattern — the same one used by the GitHub and AWS CLIs. The user runs a login command, sees a short code and a URL, authorizes in a browser (possibly on another device), and the CLI polls until it receives a token. The client is public (no embedded secret), tokens are short-lived with a refresh token so revocation works as a kill switch, and user codes omit ambiguous characters.
7.2 Agent calls — scoped bearer tokens
The token is bound to the user's account and scoped: pages:read (find/list/get), pages:write (publish/update/delete/visibility), and — separately and at higher consent — domains:bind. The agent's default token does not carry domains:bind; pointing an owned domain at agent-generated content is a privileged action gated to a human or a step-up grant. Scopes express the capability split natively.
7.3 Standards-based discovery (the distribution thesis, in practice)
Two layers. The works-today layer is a SKILL.md plus a CLI binary the agent self-discovers and installs, advertising the verbs and the account's current recipe palette. The works-as-agents-catch-up layer publishes /.well-known/oauth-authorization-server (RFC 9728) and an endpoint catalog (RFC 9727) so a sufficiently modern agent can discover and authenticate to the platform with no setup, no docs, and no bespoke integration. That is the whole cross-agent thesis expressed in open standards rather than a proprietary protocol.
8. Trust, safety, and legal (non-optional)
Public, persistent, agent-generated pages carry real liability — precisely the liability that led incumbents to keep similar features private. This is the most serious area of the product and must ship at launch, not after.
8.1 Mandatory CSAM reporting
Under U.S. law (18 U.S.C. § 2258A, as expanded by the REPORT Act), a hosting provider with actual knowledge of apparent child-exploitation material must report to NCMEC's CyberTipline as soon as possible and no later than 60 days, and must preserve the material and related data. Reporting and preservation carry liability protection unless done recklessly; failure to report carries penalties up to roughly $850,000 for providers under 100M monthly users. NCMEC has specifically flagged rising volumes of AI-generated CSAM, which puts an agent-publishing platform squarely in the regulatory path.
8.2 What this requires us to build at launch
	•	A reachable abuse-report intake (monitored endpoint/address), designed for NCMEC CyberTipline reporting.
	•	A fast global kill operation: purge edge cache + tombstone the page record + quarantine the R2 object. The frozen-static design makes this clean — one object, one cache key, gone in seconds.
	•	Preserve-not-delete: the law requires retaining reported material, so “delete” for abuse cases means quarantine to a sealed store, not hard-delete. The page lifecycle needs a distinct quarantined state separate from tombstoned.
	•	Proactive hash-matching against known-CSAM lists, to move from reactive (actual-knowledge-only) to a defensible posture as volume grows.
8.3 Forward-looking
Pending legislation (the STOP CSAM Act) points toward mandatory notice-and-takedown mechanisms and civil liability for reckless hosting. Building a first-class notice-and-takedown path now is cheap insurance against where the law is heading.
8.4 Other abuse
Phishing and malware are the high-volume cases. The same kill path applies; add domain-reputation checks at publish and rate limits per account. Prior in-house work on probabilistic prompt-injection / content scoring is directly reusable for a publish-time content classifier.
9. Verified technical & legal risks
Risk
Severity
Finding & mitigation
Shortwind expander runs in Workers
Low
Node compat on Workers is strong (fs, crypto, streams, buffer supported). Likely fine if the engine is pure JS string transformation. Fallback: Cloudflare Containers (GA, billed per CPU-cycle) via service binding. Settle with a one-afternoon spike: install the engine in a Worker and call expand().
Custom domains at scale
Low
Cloudflare for SaaS: 100 hostnames free, then $0.10/hostname/month up to 50,000 before any sales conversation. Pass-through in metered billing. Caveats: cert issuance is rate-limited (queue bursts); hostname state-change webhooks are enterprise-only (poll the details endpoint).
Moderation / takedown
Moderate — the real one
Mandatory NCMEC reporting on actual knowledge within 60 days; preserve-don't-delete; penalties up to ~$850K; STOP CSAM points at mandatory notice-and-takedown. Build quarantine state, kill-and-seal delete, abuse intake, and hash-scanning at launch. The frozen-static design makes the technical takedown easy; the legal wrapper is the work.
Incumbent ships public sharing
Strategic
An incumbent could add public sharing and erase the wedge. They have chosen not to because of exactly the liability in Section 8. That makes the gap durable but means safety/moderation is the moat, not a footnote.
10. Phasing
Phase 0 — Spike (de-risk)
	•	Prove the Shortwind engine runs in a Worker (or fall back to a Container). Binary outcome; do this first.
	•	Stand up device-flow auth with one scope and a single publish → URL path.
	•	Prove the global Shortwind home: shortwind init --global + login creating ~/.shortwind/ synced to a cloud account, usable from an arbitrary directory.
Phase 1 — Core (launch)
	•	Verbs: find, publish, update, get, delete, visibility. Single-file unit. Frozen static serving on R2 + Worker.
	•	Server-side identity (slug + ID), idempotent publish, global Shortwind home (~/.shortwind/) with lockfile diffing + cloud sync; local repo recipes/ override.
	•	Trust & safety: abuse intake, quarantine/tombstone lifecycle, kill path, hash-scanning.
	•	SKILL.md + CLI discovery; human dashboard for oversight + audit log.
Phase 2 — Owned presence
	•	bind-domain via Cloudflare for SaaS, human-gated; custom-domain billing.
	•	Standards discovery endpoints (RFC 9728 / 9727).
Phase 3 — Fast-follow
	•	Bundles (linked multi-file deploys, one entry point), resolving cross-file link-before-deploy.
	•	Optional: visibility tiers, expiry, project grouping.
11. Open questions
	•	Name and namespace — settle domain + npm scope + CLI command together, since the agent says the command aloud (cairn publish / stet push).
	•	Recipe-change detection — resolved: send touched bodies + lockfile, platform diffs and dedupes (the Git-object round-trip is a later optimization). Open: confirm global-home behavior when switching between multiple cloud accounts on one machine.
	•	Build-time vs. runtime expansion is settled as build-time; confirm the engine has no Worker-incompatible dependency in the Phase 0 spike.
	•	Default visibility per context — private working pages default live/unlisted; public artifacts default frozen/pinned. Confirm exact defaults.
	•	Pricing meter — publishes vs. storage vs. custom domains; align with the cost shape in 6.4.
